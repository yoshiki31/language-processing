# VM理解度テスト

MiniC++ VMの理解度を確認するための説明式テストです。
各問題のすぐ下に解答例を書いています。

---

## 1. MiniC++のソースコードは、VMで実行されるまでにどのような流れで処理されますか。

### 解答例

MiniC++のソースコードは、まず字句解析でトークン列に変換されます。
次に構文解析でASTに変換され、そのASTをコンパイラがVM用のバイトコードに変換します。
最後に、VMがそのバイトコードを1命令ずつ実行します。

```text
ソースコード
  -> トークン列
  -> AST
  -> バイトコード
  -> VMで実行
```

---

## 2. VMがASTを直接実行せず、バイトコードを実行する理由を説明してください。

### 解答例

ASTは構文構造を表す木構造なので、人間やコンパイラには扱いやすいですが、VMが順番に実行するには少し複雑です。
バイトコードに変換すると、`push`、`add`、`call`、`ret` のような単純な命令列になります。
そのため、VMはプログラムカウンタを進めながら、命令を1つずつ処理できます。

---

## 3. スタックマシンVMとはどのようなVMですか。

### 解答例

スタックマシンVMは、計算途中の値をスタックに積みながら処理するVMです。
例えば `3 + 4` を計算する場合、まず `3` を積み、次に `4` を積み、`add` 命令で2つの値を取り出して足し算し、結果の `7` を再びスタックに積みます。

```text
push 3
push 4
add
```

最終的にスタックには `7` が残ります。

---

## 4. VMの `@stack` は何のために使われていますか。

### 解答例

`@stack` は、式の計算途中の値、関数の引数、戻り値などを一時的に置くために使われます。
例えば足し算では、左右の値をスタックから取り出して計算し、結果をまたスタックに戻します。
関数呼び出しでも、呼び出し前に引数をスタックに積み、呼び出し処理でそれを取り出します。

---

## 5. VMの `@frames` は何のために使われていますか。

### 解答例

`@frames` は、関数呼び出しごとの実行状態を管理するために使われます。
関数を呼び出すと、新しい `Frame` が作られて `@frames` に積まれます。
`Frame` には、実行中の関数、次に実行する命令位置、ローカル変数などが入ります。
関数が戻ると、その `Frame` は取り除かれ、呼び出し元の関数に戻ります。

---

## 6. 関数呼び出し時に、新しい `Frame` が必要になる理由を説明してください。

### 解答例

関数ごとにローカル変数や実行位置が異なるためです。
例えば `main` から `f` を呼び出した場合、`main` のローカル変数と `f` のローカル変数は別々に管理する必要があります。
そのため、関数を呼び出すたびに新しい `Frame` を作り、その関数専用の実行状態を保存します。

---

## 7. `return` のとき、フレームをpopするだけでなく戻り値をスタックに戻す理由を説明してください。

### 解答例

戻り値を呼び出し元が使えるようにするためです。
関数が終了すると、その関数の `Frame` は不要になるのでpopします。
しかし、戻り値まで消してしまうと、呼び出し元は関数の結果を受け取れません。
そのため、戻り値を一度取り出してからフレームをpopし、その戻り値をスタックに戻します。

---

## 8. `puts` や `gc` がユーザー定義関数ではなく、組み込み関数として扱われている理由を説明してください。

### 解答例

`puts` や `gc` は、VMの外部出力やヒープ管理に直接関係する特別な処理だからです。
ユーザー定義関数はMiniC++のバイトコードとして実行されますが、`puts` はRuby側の出力に接続し、`gc` はVM内部のヒープを操作します。
そのため、通常の関数呼び出しとは別に、VMの `do_call` の中で名前を見て特別扱いしています。

---

## 9. `Value` クラスを使って値を表現している理由を説明してください。

### 解答例

VMのスタックやローカル変数には、整数だけでなく配列への参照も入るためです。
単純なRubyの整数だけを置く設計だと、値が整数なのか、ヒープ上のオブジェクト参照なのか区別できません。
そこで `Value` クラスを使い、値本体とタグを一緒に持たせています。

```text
Value.int(10)      -> 整数
Value.object(ref)  -> ヒープオブジェクトへの参照
```

---

## 10. タグ付き値表現とは何ですか。

### 解答例

タグ付き値表現とは、値に「この値は何型か」という情報を付けて管理する方法です。
今回の実装では、`Value` が `:int` や `:object` のようなタグを持っています。
演算や配列アクセスのときにこのタグを確認することで、不正な値の使い方を検出できます。

---

## 11. 演算時に `int?` のような型チェックが必要な理由を説明してください。

### 解答例

VMのスタックには整数だけでなく、配列への参照も載るからです。
もし型チェックをしないと、配列参照に対して足し算をしてしまう可能性があります。
そのため、`+` などの整数演算では、左右の値がどちらも `int` であることを確認してから計算します。

---

## 12. 型が増えた場合、演算できるかどうかはどのように判断すればよいですか。

### 解答例

演算子と左右の値のタグの組み合わせで判断します。
例えば `+` の場合、`int + int` は許可し、`int + object` はエラーにします。
将来文字列を追加するなら、`string + string` を許可する設計も考えられます。

```text
int + int       -> OK
int + object    -> NG
object + object -> NG
```

---

## 13. `int[] values = new int[3];` はC言語の構文ではない理由を説明してください。

### 解答例

C言語では、固定長配列は `int values[3];` のように書きます。
動的確保の場合は `malloc` を使い、`int *values = malloc(...)` のように書きます。
一方、`int[] values = new int[3];` はJava風の配列宣言とC++風の `new` を組み合わせた、MiniC++用の独自構文です。

---

## 14. `new int[3]` を実行したとき、配列本体がローカル変数ではなくVMヒープに置かれる理由を説明してください。

### 解答例

配列は複数の要素を持つオブジェクトであり、関数呼び出しや代入をまたいで共有される可能性があるためです。
ローカル変数に配列本体を直接入れるのではなく、VMヒープに配列本体を置き、ローカル変数にはその参照を入れます。
これにより、同じ配列を複数の変数や関数から参照できます。

---

## 15. `Heap`, `Entry`, `ObjectRef`, `IntArray`, `Value` の関係を説明してください。

### 解答例

`Heap` はVM上のオブジェクトを管理する場所です。
`Heap` の中には `Entry` が入り、`Entry` はオブジェクト本体とGC用のマーク情報を持ちます。
配列の場合、オブジェクト本体は `IntArray` です。
`IntArray` の中には、配列要素として `Value` が入ります。
ローカル変数やスタックには、配列本体ではなく `ObjectRef` を持つ `Value.object(...)` が入ります。

```text
Value.object(ObjectRef)
  -> Heap
    -> Entry
      -> IntArray
        -> Value.int(...)
```

---

## 16. ヒープからオブジェクトを回収するとき、ヒープ配列を詰めていない理由を説明してください。

### 解答例

ヒープ配列を詰めると、オブジェクトのアドレスが変わるからです。
例えば `heap[2]` にあった配列を `heap[1]` に移動すると、その配列を指していた `ObjectRef(2)` も `ObjectRef(1)` に更新しなければなりません。
更新対象は、スタック、ローカル変数、配列内の参照などです。
今回の実装ではGCを単純にするため、アドレスを変えず、回収済みスロットを `nil` にする方式にしています。

---

## 17. 今回実装したMark & Sweep GCの流れを説明してください。

### 解答例

Mark & Sweep GCは、まずルートから辿れるオブジェクトをマークします。
今回のルートは、VMスタックと各関数フレームのローカル変数です。
マークが終わったら、ヒープ全体を走査し、マークされていないオブジェクトを回収します。

```text
1. スタックとローカル変数を見る
2. 参照されている配列をマークする
3. ヒープ全体を見る
4. マークされていない配列を回収する
```

---

## 18. Mark & Sweep GCが循環参照に対応できる理由を説明してください。

### 解答例

Mark & Sweepは、参照数ではなく「ルートから到達できるか」で生存判定するためです。
たとえ `A -> B`、`B -> A` のように互いに参照していても、スタックやローカル変数から到達できなければマークされません。
そのため、循環しているオブジェクトでも、ルートから到達不能ならスイープで回収できます。

---

## 19. `gc()` サンプルで本当に回収できているか、どのように確認できますか。

### 解答例

通常のCLI実行では戻り値しか表示されないため、Ruby側からVMを直接作って `vm.heap.size` を確認すると分かりやすいです。
例えば、配列を2個作って片方を参照不能にしたあと `gc()` を呼ぶと、実行後の `heap.size` が `1` になります。
同じ処理で `gc()` を呼ばない場合は、`heap.size` が `2` のままです。

```text
GCなし: heap.size 2
GCあり: heap.size 1
```

---

## 20. 今回のVM実装で、今後拡張できる点を説明してください。

### 解答例

今後の拡張としては、自動GC、ヒープスロットの再利用、ヒープのコンパクション、配列の中に配列参照を入れた場合の再帰的マーク処理などがあります。
また、型を増やすなら `bool` や `string` を `Value` に追加し、演算時のタグチェックも拡張する必要があります。
今回の実装は、関数呼び出し、タグ付き値表現、int配列、VMヒープ、明示的なMark & Sweep GCまでを扱える段階です。
